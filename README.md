# CJ — инсоляция в SketchUp

Ветка C++ движка: `codex/cpp-insolation-engine`. Расчёт использует исходные 510 направлений: одна выборка соответствует одной минуте. Методика пользователя: 90 минут непрерывно либо 120 минут прерывисто с сегментом не менее 60 минут.

## Работа в SketchUp

1. В **«Настройки CJ»** задайте размеры окна, вид результата (**Линии / Поверхность / Итоги**), радиус маркера и способ расчёта.
2. **«Инсоляция — выбрать точки»**: самостоятельно расставьте точки кликами. Enter сохраняет их и запускает расчёт; Backspace убирает последнюю; Esc отменяет выбор.
3. Точки сохраняются отдельными группами в SKP. Выделяйте их рамкой или с Shift и перемещайте обычным Move (M). **Автоматических и динамических расчётов нет.**
4. **«Пересчитать точки CJ»** пересчитывает выделенные точки; без выделения — все видимые незаблокированные точки. Предыдущие результаты заменяются. **«Выделить точки CJ»** выделяет все доступные точки.
5. **«Вставить окно CJ»** размещает окна с размерами из настроек. **«Рассчитать окна CJ»** рассчитывает их встроенные точки. [Окна и параметры](WINDOW_COMPONENTS.md).

Поиск точки выбором окна, стены и поверхностей удалён. Видимые номера скрыты. Зелёный цвет означает свободное направление, красный — затенение. Точки и результаты сохраняются в SKP. В окне прогресса доступна отмена; изменения можно отменить через Undo.

В папке тегов **«Инсоляция»** результаты разделены на **«Проходят»** и **«Не проходят»**. В каждой подпапке свои зелёные и красные лучи/сегменты, сферы, плоскости окон и подписи: можно скрывать категорию целиком либо отдельный вид её графики. При построении результатов прежние результаты распределяются по сохранённой оценке без повторного расчёта. Сохранённые точки для выбора и перемещения остаются отдельными объектами.

Окно расчёта загружается до начала подготовки модели. Оно показывает отдельные этапы подготовки, расчёта и построения результата, счётчик времени и процент выгрузки геометрии. Пока читается модель и работает C++ движок, отображается движущийся индикатор: сохранённый EXE не сообщает промежуточный процент. Выгрузка выполняется порциями, чтобы интерфейс и отмена работали во время подготовки.

## C++ расчётчик

Плагин передаёт снимок видимой геометрии отдельному локальному `cj_engine.exe`. Движок строит BVH и параллельно ищет ближайшие пересечения лучей с треугольниками. Он не обращается к SketchUp API и не требует Codex, Python или моста на компьютере пользователя. EXE включается в RBZ при сборке.

Рабочий движок сохранён в `native/stable/`; новые сборки создаются отдельно в `native/build/experimental/`. Плагин и упаковщик RBZ используют только рабочую версию с проверкой SHA256. Экспериментальные сборки автоматически не подхватываются. Для продолжения работы над C++ без создания EXE: `./native/build.ps1 -SyntaxOnly`.

Обычные отверстия в гранях, вложенные группы, повороты, отражения и масштабирование проверены сравнением со SketchUp. Изображения экспортируются через их внутреннюю геометрию. Скрытые объекты, грани, теги и папки тегов исключаются независимо от показа скрытого в окне. Для приклеенных компонентов с автоматическим прорезанием проёма и включённых активных сечений используется штатный расчёт SketchUp. При отсутствии EXE также используется SketchUp. Выбор **«SketchUp (совместимость)»** всегда включает исходный расчёт.

На синтетической сцене из 1000 блоков проверено 16 448 лучей без расхождений: SketchUp — 1139 мс, C++ с экспортом геометрии — 102 мс. Это один тест, без построения результатов. На рабочей модели проверены 6120 лучей и 4 035 133 видимых треугольника: солнце/тень совпали во всех случаях, максимальная разница расстояний 0,000716 мм. SketchUp — 16,84 с; C++ с экспортом — 25,70 с (экспорт 23,55 с, процесс движка 2,15 с). На этой модели первый запуск C++ пока медленнее из-за экспорта.

После оптимизации Ruby-экспорта на той же модели проверены три точки / 1530 лучей: подготовка и расчёт сократились с 26,40 до 12,83 с, из них экспорт — с 24,29 до 10,67 с. Результаты совпали со SketchUp; построение графики в этот замер не входит. Используется тот же рабочий EXE.

Дополнительное упрощение преобразований координат дало в следующем замере 12,21 с (экспорт 10,02 с); 1530 лучей снова совпали по солнцу/тени. Это отдельный замер, время зависит от нагрузки компьютера. Шкала выгрузки проверена в настоящем окне SketchUp, включая отмену и сохранность модели.

Подготовленная геометрия теперь повторно используется в пределах сеанса модели. Перемещение/добавление точек и построение результатов CJ не требуют её повторного чтения. Изменение геометрии, скрытия объектов, используемых тегов/папок, режима сечений, Undo/Redo или отмена операции сбрасывают снимок; следующий расчёт готовит всю сцену заново. При открытом редактировании компонента повторное использование отключено. Отслеживание изменений только сбрасывает снимок, расчёты запускаются по кнопке. Снимок хранится во временной папке, не в SKP или Git; после закрытия модели/приложения создаётся заново.

На повторно открытой рабочей модели (3 701 513 видимых треугольников, 1530 лучей) свежая подготовка заняла 8,00 с, повторная — 0,64 с; повторный C++ расчёт вместе с подготовкой — 2,58 с без графики. Все лучи совпали со SketchUp. Первый запуск по-прежнему требует полной подготовки; передача бинарной сцены и построение BVH рабочим EXE пока повторяются. Это не обновление отдельных объектов и не динамический расчёт.

## Разработка

Первый отдельный адаптер для Rhino 7 Windows: [запуск панели и ограничения прототипа](rhino/README.md). Использует тот же сохранённый C++ движок; файлы SketchUp-плагина не меняет.

- [Сборка и протокол движка](native/README.md).
- `native/test_engine.py` — независимое сравнение пересечений и проверка протокола.
- `dev/cpp_checks.rb` — сравнение C++ со SketchUp на временной сцене; нужен пустой тестовый файл.
- `dev/workflow_checks.rb` — сохранение точек, замена результатов и настройки.
- [Отдельный мост CJ Bridge](tooling/README.md) не входит в RBZ, имеет собственный загрузчик и панель.
